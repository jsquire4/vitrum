## Section G — Items to fix

### P0 — default-path correctness (affects what users render by default)

#### G-P0.1 ReSTIR-DI target function p̂ evaluated with different normals across passes

- **Where:** `packages/walkaround-hybrid/src/shaders/restirCastPrimary.wgsl.ts:61` — `s.normal = hit.normal;` (geometric face normal). Consumed by temporal reuse (`temporal.wgsl.ts:81` `castPrimary` → `:110` `restir_di_compute_phat_from_surface(prev.lightId, curSurf)`) and spatial reuse (`spatial.wgsl.ts:91/107` → `:121/136`). Meanwhile RIS (`ris.wgsl.ts:123` + `:250` `surf.normal = normal;`) and shade (`shade.wgsl.ts:449`) overwrite the surface normal with `smoothShadingNormal(...)` before evaluating the SAME canonical p̂ (`restirPHat.wgsl.ts:35-52`, which reads `surf.normal`).
- **Bug:** `restirPHat.wgsl.ts:6-14` states the Bitterli 2020 §4.3 invariant ("p̂ … MUST be identical across all three passes"). The W2-C7 refactor canonicalized the *formula* but not the *input*: temporal/spatial re-weight reservoirs with the geometric normal while RIS selected and shade integrates with the shading normal → biased reuse on any smooth-normal (curved) geometry. Masked on flat Cornell walls (smooth ≡ geometric), which is why every existing A/B stayed green.
- **Fix:** populate `PrimarySurface.normal` with the smooth shading normal inside `castPrimary` (keep the geometric normal separately for ray offsets, the pattern the 4 primary passes already use per `smoothNormals.test.ts`), or thread both normals and make p̂ read the shading normal.
- **Acceptance:** a converged curved-geometry (sphere in Cornell) A/B of reuse-on vs RIS-only shows no systematic bias; `smoothNormals.test.ts` extended to pin `castPrimary`'s normal source (the exact gap its current regex assertions leave open).

#### G-P0.2 DDGI irradiance convention — blend stores a cosine-weighted MEAN, both receivers consume it as irradiance E (π-factor inconsistency)

- **Where (producer):** `packages/walkaround-hybrid/src/ddgi/wgsl/probeUpdateBlend.wgsl.ts:149-156` — `newColor += ray.hitRadiance * weight; totalWeight += weight; … newColor = newColor / totalWeight;` (cosine weights `max(0, n·d)`). The cosine-weighted mean of incoming radiance equals **E/π**, not E (for uniform L: mean = L, true E = πL).
- **Where (consumers):** `applyDDGIShading.ts:168-175` — `(albedo/π) · E_ddgi` with the comment "Atlas holds true irradiance E per Sweep M7"; and `risGi.wgsl.ts:251` — `Lo = irrAtXs * xsMat.rgb * INV_PI;`. No π reconstruction exists anywhere between texel and consumption (verified: no compensating factor in `ddgiSampleWgsl.ts` or `probeUpdateRays.wgsl.ts`).
- **Bug:** the chain composes to `albedo·E/π²` — a factor **π (~3.14×) dimmer** than the Lambertian model both sites cite (Majercik 2019 §3). The receiver comment contradicts the blend's own math. `__tests__/ddgiPipeline.test.ts:372-407` explicitly documents the mean-vs-integral regime split and then tests the EMA toward mean=1 (Test 1) and the receiver formula with a hand-fed E=π (Test 2) — i.e. the suite consciously tests around the seam instead of through it.
- **Disposition needed:** either (a) it is a real ~3.1× indirect-diffuse deficit → fix the constant (multiply π at texel→E reconstruction, or consume `albedo·texel` directly since `albedo·E/π = albedo·mean`); or (b) it is an intentional calibration absorbed by the sun/sky intensity knobs → then the comments, the Majercik citation, and the tests must say so. Decide and pin; do not leave the comment claiming texel=E.
- **Acceptance:** a self-validating uniform-room harness through the REAL producer chain (probe rays → blend → receiver, no hand-fed E) lands at `Lo = albedo·L`; direct-vs-indirect relative energy checked on GPU; goldens re-captured if the constant changes (they currently encode today's behavior).

#### G-P0.3 pt-webgl fork: scalar hero throughput crushes interior-bounce color in the DEFAULT (non-spectral) path

- **Where:** `packages/three-gpu-pathtracer/src/shader/structs/surface_record_struct.glsl.js:81-86` — `ScatterRecord { … float throughput; }` (scalar). Built from the RGB BSDF result via `result.throughput = heroScalarFromRgb( resultColor, heroWavelength )` (`bsdf_functions.glsl.js:701`; also `:608`, `:683`). Accumulated scalar in the main loop (`PhysicalPathTracingMaterial.js:1030` `state.throughput *= scatterRec.throughput / scatterRec.pdf;`), re-expanded for every radiance add via `throughputRgb = wavelengthToRGB( state.wavelength, state.throughput, state.wavelengthPdf )` (`:591`, consumed at `:648/652/666/688/970`). `heroScalarFromRgb` (`util_functions.glsl.js:29-35`) is a smoothstep wavelength projection; the default render state initializes `wavelength = 550.0` (`render_structs.glsl.js`).
- **Bug:** even with spectral rendering OFF (the default), the carried path throughput is a scalar — at λ=550 the projection weights are (tR=0, tG=1, tB=0), i.e. **interior-bounce BSDF color collapses to ≈ its green channel**. NEE's per-vertex RGB evaluation preserves first-order color bleed (which masks the issue), but any path *through* a saturated surface is crushed: a (0.65, 0.05, 0.05) red wall's interior bounce carries 0.05 instead of 0.65 — ~13× darker. Fork-introduced (the upstream carries vec3 throughput); this is the single most consequential default-path fidelity item found.
- **Caveat:** code-verified mechanism; **magnitude requires a render A/B against an independent reference** (pt-webgpu on the same scene, or pre-fork upstream) — NOT against existing baselines, which were captured after the change and may share it (the F-TLAS1 lesson).
- **Fix:** restore `vec3` throughput for the non-spectral path (carry vec3 + hero scalar in parallel, select by the spectral flag), or demonstrate via A/B that the impact is below perceptual threshold and document the approximation.
- **Acceptance:** converged Cornell A/B vs pt-webgpu shows matched multi-bounce color bleed; spectral mode output unchanged.

#### G-P0.4 three-bindings: silent data drops and wrong-space conversions

All verified at the cited lines; each is a forward/reverse asymmetry a consumer cannot see without reading source.

- **(a) Directional/spot light direction computed in LOCAL space.** `lights.ts:82-84` (directional: `dl.position.x - dl.target.position.x` …) and the spot arm (`:133-153`) read local positions, ignoring parent world transforms — wrong direction for any light nested under a transformed node. `sceneFromThreeJS` already calls `updateMatrixWorld(true)`; derive from `matrixWorld` (the rect-area arm at `:99-105` already does).
- **(b) RectAreaLight axes double-scale under non-uniform parent scale.** `lights.ts:103-104` takes world-matrix basis columns (which carry scale) and multiplies by half-width/height — scale applied twice. Normalize the basis columns first.
- **(c) `convertInstancedMesh` / `convertSkinnedMesh` drop `uv1` + `colors`.** `mesh.ts:437-439` and `:555-557` extract only `uv`/`tangent`/`index`, while the contract declares `uv1` and `colors` on both primitive kinds (`core/src/scene/primitives.ts:36/38` and `:107/109`) and `convertMesh` extracts them. Silent attribute loss.
- **(d) Reverse path (`vitrumSceneToThree`) drops opacity/alpha/AO/lobe maps.** `vitrumSceneToThree.ts:55-63` forwards only 7 base maps (`PHYSICAL_MATERIAL_TEXTURE_FIELDS`); no handling anywhere in the file for `opacity`, `alphaMode`/`alphaCutoff`, `aoMap`(+intensity), or any clearcoat/sheen/iridescence/anisotropy map — all of which the FORWARD path (`convertMaterial`) produces. Consequence: a core-authored alpha-blend or AO'd material loses those when the walkaround engine synthesizes its THREE scene (BVH/DDGI source) or when fed to pt-webgl — transparency only survives via `transmission>0`. The round-trip test covers only `map`, masking the gap. Extend the apply list (the dispose list is already derived from it, so it follows for free).
- **(e) Animation: `THREE.InterpolateSmooth` mislabeled as glTF `CUBICSPLINE`.** `animationImport.ts:25-31` — THREE smooth tracks carry no explicit in/out tangents; a consumer evaluating the emitted sampler per glTF cubic-spline layout (as `core`'s `sampleAnimationClip` does) reads tangents that aren't there. Map smooth → `'LINEAR'` (with a warning) or synthesize tangents.
- **Acceptance:** nested-light unit tests (world-space direction); attribute-completeness tests for instanced/skinned conversion; a forward→reverse material round-trip test over the full `MaterialSpec` surface; an InterpolateSmooth import test.

- **The contract is real and honored.** `BACKEND_PROMISE_LEDGER` is a machine-checkable truth table pinned by tests in all three backends; `BackendSupportDetails` matches behavior; `partitionSceneBySupport` is the single warn+skip layer; `wrapWithIdempotentDispose` forwards every optional method with correct capability gating and per-method disposed semantics encoded as data; `createProgressiveEngine` computes the cross-backend limit union, preflights capabilities with actionable errors, and destroys the device on every throw path.

### Test reality (what green means)

~40% STRONG / ~45% MEDIUM / ~15% WEAK in the flagship suite. STRONG = real oracles (GRIS math to 1e-12, BDPT MIS vs independent reimplementation, VNDF normalization, adjoint vs FD, PPG CPU/GPU traversal equivalence, byte-layout goldens, genuine lifecycle/race pins). The structural discipline is excellent: no `.only`/`.skip` abuse anywhere (2 env-gated GPU acceptance suites total); opt-in features pinned to be byte-identical when OFF. The systemic boundary: **in-tree tests never execute shaders** — WGSL is pinned by string goldens; rendered radiometric correctness lives exclusively in the external GPU harness, outside `npm test`. That is a deliberate architecture, but it is exactly why G-P0.1/0.2/0.3 and G-P1.1 sat green: each is invisible to string goldens, flat-wall test scenes, and same-estimator A/Bs.
