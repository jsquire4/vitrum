## Summary

- **Total files audited:** 22 (all text; 0 binaries; 0 autogenerated)
- **Top-level claim under test:** `_staging/README.md` and the project
  `CLAUDE.md` both state "Extraction: `_staging/legacy-source/` contains
  only host-app React/Redux files intentionally not extracted." This
  audit verifies that claim.

### Verdict on the README claim

**Mostly true, with three small violations.** Every `.tsx` file is host
React/Redux glue and should stay. But three `.ts` data-table files
(`cameraLookPresets.ts`, `outdoorHdri.ts`, `outdoorScenePresets.ts`) are
not host-only — they are pure data tables / pure functions with zero
React or Redux imports. The first two are referenced **only** by host
`.tsx` files in staging; the third (`outdoorScenePresets.ts`) imports
`outdoorHdri.ts`. They could be lifted into `@vitrum/pt-webgl` as
optional preset registries that hosts can opt into, or moved into
`examples/` as reference data. The grey zone is whether vitrum wants to
ship preset registries or leave that to consumers. **Recommendation:**
not engine-essential; leave staged unless an example needs them.

The README's enumerated table also has one small inaccuracy:
`walkaround/useSceneBVH.ts` is **no longer a duplicate** of
`walkaround/lib/useSceneBVH.ts` — the two now have different return
types (`SceneBVH` vs `SceneBVHCommonResult`) and different signatures
(`trigger?` vs `opts, trigger?`). See DUPLICATE table below.

### Note on dangling refs in `ptEnvironment.ts`

`ptEnvironment.ts:7` imports `PT_IBL_INTENSITY` and
`PT_BACKGROUND_INTENSITY` from `'./lightingIntensityTable'` — but the
actual `packages/pt-webgl/src/lightingIntensityTable.ts` exports only
`COLOR_TEMP_HEX`, `SUN_INTENSITY`, `getSunIntensity`, and the lumen
converters. The two intensity-table records the staging file expects
**do not exist anywhere in the repo** (grep confirms — only ref is the
staging files themselves).

This is dead reference glue: `ptEnvironment.ts` would not compile
against the current `packages/pt-webgl` if the host app tried to use
it as-is. The host would need to either define the tables locally or
extract them. This is a small staging-rot finding, not an extraction
gap — the host owns the IBL-intensity policy and the engine deliberately
does not. **No action required**, but a future re-integration of this
file by the host will hit the dangling import.

| File | Target package | One-line description | Effort |

| `outdoorScenePresets.ts` | `examples/shared/` | Adds 4 named outdoor HDRI overrides on top of `outdoorHdri.ts` (`sunnyDay`/`overcast`/`goldenHour`/`forest`). Asset-policy table. Depends on `outdoorHdri.ts`. | S |

### Why these three only got soft-recommended

vitrum's contract (per `CLAUDE.md` principle 2) is **host-agnostic** —
engine accepts a scene + camera + frame inputs and renders. The engine
deliberately does **not** decide:

- What HDRI to load. Hosts hand the engine a baked envmap; HDRI URLs
  and Polyhaven sourcing are host policy.
- What post-FX chain to run. The engine outputs an HDR radiance buffer;
  bloom / DoF / vignette / grain are host-side EffectComposer concerns.
- What time-of-day buckets exist. The host has its own diurnal model;
  the engine takes a sun direction and intensity.

So a stricter reading of vitrum's design says these three files belong
in `examples/shared/`, not in `packages/`. If you ever build a
`hero-product-viz` or `hero-viewer` example that loads a Polyhaven
HDRI and applies the documentary-look post chain, **lift them there
verbatim** — no transformation needed. None imports React.

### Top-3 highest-value extractions

There aren't any high-value engine extractions left in
`_staging/legacy-source/`. The engine-shaped value was already
lifted in the Phase 6 / Phase 7 extraction sprints. What remains is
either:

1. Host React/Redux glue (intentionally not extracted), or
2. Three small data tables on the boundary between engine policy and
   host policy (recommend `examples/shared/`).

**If forced to rank** the three candidates by hypothetical extraction
value:

1. `cameraLookPresets.ts` — most general, three named "camera response"
   bundles are reusable across any vitrum host that needs photographic
   post-FX. Cleanest fit for a future `@vitrum/post-fx-presets` package
   that wraps `@react-three/postprocessing` for vanilla and R3F hosts.
2. `outdoorHdri.ts` — generic time-of-day → HDRI URL lookup, but tied
   to Polyhaven's asset catalog. Belongs in `examples/shared/` unless
   vitrum decides to ship a Polyhaven HDRI loader as a separate package.
3. `outdoorScenePresets.ts` — narrowest, just four named overrides on
   top of (2). Lift only if (2) is lifted.

None of the three is gating any vitrum library work. They are an
extraction nice-to-have, not a must.

### `useSceneBVH.ts` duplicate-pair status (README correction)

The README's "Remaining files" table claims
`walkaround/useSceneBVH.ts` is "Duplicate of `walkaround/lib/useSceneBVH.ts`
— delete the top-level copy when host app is updated."

**That claim is no longer accurate.** Read the two files side by side:

| File | Returns | Opts param | Imports |
|------|---------|-----------|---------|
| `walkaround/useSceneBVH.ts` | `SceneBVH \| null` | none (only `trigger?`) | `./bvhCompute` (RC adapter) |
| `walkaround/lib/useSceneBVH.ts` | `SceneBVHCommonResult \| null` | `SceneBVHCommonOpts` | `./bvhCommon` (generalised) |

They are **sibling host hooks** at different abstraction levels: the
top-level file is RC-specific (uses RC's `bvhCompute` with its
`StorageBufferAttribute` typing), the `lib/` version is the
generalised-over-engines version. The `lib/` version is the future,
but the top-level file is not a stale duplicate of it. Update the
README claim or consolidate the two host hooks first; deleting the
top-level today would break the RC engine path.

Neither file should be extracted to a vitrum package — both import
host-relative `bvhCompute.ts` / `bvhCommon.ts` files that live in the
host app, not in `@vitrum/shared-bvh`. The library has its own BVH
construction; these hooks are React adapters around the **host's**
copy of the BVH builder.
